# WindowKeeper

把窗口布局变成一次点击。

你有没有过这种时候：坐下来开工，要先把浏览器拖到左边、编辑器拖到右边、微信甩到副屏、
终端拉到下面——每天重复一遍，每次都要微调半天才对得齐。

Windows 自带的 `Win` + 方向键只能做「左半屏 / 右半屏 / 四分之一」这几种固定形态，
而且**它记不住你的布局**，更不会在换了显示器之后帮你摆回去。

WindowKeeper 就是干这个的：**把现在这一屏窗口的大小和位置记下来，以后一键回来。**

---

## 它能做什么

| 功能 | 说明 |
|---|---|
| **捕获** | 一键记下当前所有窗口的位置、尺寸、所属显示器 |
| **还原** | 一键把窗口摆回记录的位置，精确到像素 |
| **预设** | 存多套布局，比如「写代码」「剪视频」「开会投屏」 |
| **全局热键** | 在任何程序里按 `Ctrl+Alt+1` 就能切布局，不用切窗口 |
| **托盘常驻** | 常驻系统托盘，不占任务栏 |
| **预演** | `--dry-run` 先看会怎么动，确认了再真动 |
| **跨显示器** | 支持多屏、不同缩放率、含负坐标的副屏 |
| **导入导出** | 布局可以导出成 JSON 发给别人 / 备份 / 换机迁移 |

## 直接用（不需要装 Python）

`dist\WindowKeeper.exe` 是**单文件绿色版**，26 MB，双击就能用，不需要装 Python 或任何依赖。

```
WindowKeeper.exe                双击 → 常驻托盘，热键生效
WindowKeeper.exe ui             打开主界面（不带托盘）
WindowKeeper.exe apply 工作     带参数就是命令行，用法见下面「命令一览」
```

**第一次用，建议这样走一遍：**

1. 把窗口都摆成你想要的样子（浏览器左边、编辑器右边……）
2. 双击 `WindowKeeper.exe`，托盘出现一个蓝色四宫格图标
3. **双击托盘图标**打开主界面 → 点左上角「捕获当前布局」→ 起个名字，比如 `工作`
4. 在主界面上选中这个预设，点「设置热键…」，**直接按下** `Ctrl+Alt+1`（不用手打）
5. 去把窗口弄乱，按 `Ctrl+Alt+1` → 窗口就回去了

想关机后自动生效：把 `WindowKeeper.exe` 的快捷方式丢进
`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`（Win+R 输入 `shell:startup` 回车）。

**删掉就是卸载**——程序不写注册表，唯一的数据在 `%APPDATA%\WindowKeeper\`
（也就是 `C:\Users\<你>\AppData\Roaming\WindowKeeper\`），里面是纯 JSON，
删掉这个目录就干净了。

**注意**：Windows 本身会在通知区域隐藏不常用的图标。
第一次跑如果托盘没看到图标，点通知区域那个 `^` 小箭头展开，
把 WindowKeeper 拖到外面常驻。

## 命令一览

```
wk list                        列出所有预设
wk windows                     列出当前可用窗口
wk monitors                    列出显示器配置

wk save <名称>                 把当前布局保存为预设
    -a, --all                  包含最小化的窗口
    -f, --force                同名时覆盖
    --only msedge.exe notepad.exe   只捕获指定进程

wk apply <名称|序号>           还原
    -n, --dry-run              只预演，不真动
    --no-activate              不把窗口带到前台

wk show <名称>                 查看预设内容
wk delete <名称>               删除
wk rename <旧> <新>            重命名
wk hotkey <名称> [按键]        设置热键（留空则清除）

wk export <文件>               导出全部预设
wk import <文件>               导入
wk tray                        启动托盘常驻
```

名称支持**前缀匹配**——存了「工作」和「工作（投屏）」，输 `wk apply 工` 若唯一匹配就直接用。

## 它是怎么做到「精确到像素」的

这部分是开发过程中踩出来的，也是这个程序真正的价值所在。
如果你只想知道怎么用，可以跳过；如果你想改代码，**这几条必须知道**。

### 1. 跨屏移动 + 改尺寸，必须分两次调用

如果一次 `SetWindowPos` 同时改变了窗口归属的显示器**和**尺寸，
系统会按**旧显示器的 DPI** 去解释你给的尺寸，等窗口落到新显示器上，
再按**新显示器的 DPI** 重算一遍。

实测：从 100% 屏往 150% 屏发 `800x600`，结果是 `1200x900`（×1.5）。

**对策**：先移位置，再单独改尺寸。两次调用。

### 2. 窗口可以合法拒绝你的尺寸

`SetWindowPos` 返回成功 **不等于**尺寸真的生效了。

窗口可以通过响应 `WM_GETMINMAXINFO` 来声明「我不接受小于 612x697」，
系统会照办。实测几个程序的自报下限：

| 程序 | 自报最小尺寸 |
|---|---|
| 记事本 | 332x202 |
| DeepSeek Harness | 612x697 |
| 微信 | 440x452 |
| 绿联云 | 1552x1115 |

所以本程序在还原后会**回读真实几何**，如果尺寸被顶到下限、且位置正确，
就报「已还原（受尺寸限制）」而不是谎报成功。

**位置没有这种约束**，所以位置永远能精确还原。

### 3. 窗口身份识别是这件事里最难的一环

只靠进程名 + 窗口标题是不够的。实测本机：

- `explorer.exe` 有 4 个窗口，**类名完全相同**
- `msedge.exe` 有 4 个窗口，**类名完全相同**
- `video-player.exe` 有 2 个窗口，**进程名、类名、标题全都相同**

所以匹配用的是加权评分：

```
进程名        45 分
窗口类名      20 分
标题完全一致  30 分
标题模糊匹配  18 分
几何位置相近  12 分
```

超过 55 分才算匹配上。**遇到「孪生窗口」（指纹完全无法区分）时，
程序会明确告诉你**，而不是随便挑一个——这是探针阶段就确认的现实，
只能交给人工指定。

### 4. 几何存储用四级回退

本机三块屏的原点是 `(0,0)` / `(23,-1600)` / `(-1440,-834)`，**含负坐标**。
绝对坐标一旦换了显示器配置就全废。所以每个窗口同时存四种表示：

1. 显示器设备名 + 绝对物理坐标 —— 配置没变时最精确
2. 显示器设备名 + 相对工作区偏移 —— 分辨率变了但屏还在
3. 相对工作区的归一化比例 —— 显示器尺寸大幅变化
4. 显示器序号 + 主屏回退 —— 设备名对不上

还原时按可用性逐级回退。判断「配置是否变过」靠的是**保存时刻的显示器矩形快照**，
不是「窗口是否落在工作区内」——因为窗口阴影和无边框最大化会让几何外溢工作区 8px，
那是正常现象。

### 5. 必须声明 DPI 感知

进程默认是 **DPI-UNAWARE** 的。不声明的话，`GetMonitorInfo` 会返回虚拟化的逻辑坐标——
本机 150% 的屏会被报成 `1707x1067` 而不是真实的 `2560x1600`。

程序启动第一件事就是调 `SetProcessDpiAwarenessContext(-4)`（Per-Monitor V2）。
**必须在任何窗口操作之前**。

### 6. 热键用 Win32 `RegisterHotKey`，不用 `keyboard` 库

做过对照实验，同一台机器、同样注入 `ctrl+alt+1`：

| 方案 | 结果 |
|---|---|
| Win32 `RegisterHotKey` + 消息循环 | ✅ 收到 `WM_HOTKEY` |
| `keyboard` 库的后台线程监听 | ❌ 回调 0 次 |

`keyboard` 库走的是低级键盘钩子（`WH_KEYBOARD_LL`），会被系统按
`LowLevelHooksTimeout` 静默摘掉。`RegisterHotKey` 是内核级注册，不受此限，
而且零第三方依赖。

**注意**：Qt 的 `nativeEventFilter` 里 `MSG` 结构的 `wParam` 偏移是 **16**，不是手算的 12——
64 位下 `message`（4 字节）后面有 4 字节对齐填充。手算偏移会读出垃圾值，
症状是**热键注册成功但按下去毫无反应**。

## 数据放在哪

```
%APPDATA%\WindowKeeper\presets.json
```

也就是 `C:\Users\<你>\AppData\Roaming\WindowKeeper\presets.json`。

托盘菜单里有「打开数据文件夹」。文件写入是原子的（先写临时文件再 `os.replace`），
中途断电不会写坏。文件里除预设外还存了一份**保存当时的显示器快照**，
用于判断「显示器配置有没有变过」——这比靠窗口位置去猜可靠得多。

## 打包

```bash
python build.py --test     # 打包 + 跑产物验收（推荐）
python build.py            # 只打包
```

产物是 `dist\WindowKeeper.exe`，单文件，26 MB。

打包配置在 `wk.spec`。**体积主要靠 `wk.spec` 里的手工剔除控制在 26MB**：

`excludes` 只作用于 Python 模块，**管不住 Qt 的 DLL**——那些是被 PySide6 的
hook 无差别收集进来的。第一版打出来 45.9 MB，其中
`opengl32sw.dll`(7.3MB)、`Qt6Quick`+`Qt6Qml`(5MB)、`Qt6Pdf`(2.35MB)、
`libcrypto`(1.77MB) 全都是用不到的。
所以 `wk.spec` 在 `Analysis` 之后、`EXE` 之前手工过滤了 `a.binaries` / `a.datas`，
剔掉 20 项，45.9 MB → 26.2 MB。

必须保留的只有 `Qt6Core` / `Qt6Gui` / `Qt6Widgets` 三个 DLL、
平台插件 `qwindows.dll`、样式插件 `qmodernwindowsstyle.dll`，
以及 MSVC 运行库。少任何一个 Qt 都起不来。

**打包前一定要先关掉正在运行的 WindowKeeper.exe**（`build.py` 已自动处理）——
否则 exe 被占用，`PermissionError` 会出现在构建的最后一步，报错信息很有误导性。

## 开发

```bash
python run_tests.py             # 全部套件（约 30 秒，推荐）
python run_tests.py --all       # 连打包验收一起（需先打包）
python run_tests.py -k log      # 只跑名字含 log 的套件
python run_tests.py --list      # 只列出套件
```

`run_tests.py` 是统一入口：内部固定工作目录、对输出编码做自适应，
所以**从任何目录都能跑**，不必记「哪个脚本要在哪个目录下执行」。

| 套件 | 项数 | 覆盖 |
|---|---|---|
| `test_engine.py` | 51 | DPI 声明、窗口枚举、标题清洗、捕获→匹配往返、几何解析、存储往返、真实还原 |
| `test_log.py` | 52 | 级别参数、双格式字段、DECISION 级别、重复 setup 不重复写、诊断包内容 |
| `test_hotkey.py` | 19 | MSG 偏移 16、无修饰键必须拒绝、热键注册/注销 |
| `test_ui.py` | 31 | 控件内容断言（**刻意不用截图比对**）、负坐标外接框、排障入口 |
| `test_e2e_user.py` | 13 | 真启**字符映射表**（进程名测试独占）→存预设→起托盘→注入**真实按键**→验证精确还原 |
| `test_packaged.py` | 15 | 对着 `dist\WindowKeeper.exe` 真跑（需先打包） |

共 **177 项**，全部对着真实窗口 / 真实 exe 跑，不用 mock。

`test_e2e_user.py` 是唯一一个**从用户视角**跑完整链路的：自己启一个字符映射表 →
用 exe 存预设绑热键 → 双击 exe 起托盘 → 把窗口弄乱 → **注入真实的 `Ctrl+Alt+9` 按键** →
核对窗口是否精确回到原位。它验证的是「用户真的能用」，而不是「某个函数对不对」。

> 这个测试原先用记事本作实验对象，但它**偶发失败**——因为 `--only` 只能按进程名过滤，
> 开发机上开着的其他记事本会被一并存进预设。改用**测试独占**的 `charmap.exe`
> 并加了两道前提守卫之后，连跑三遍稳定通过。详见 `04_BUG清单.md` 的 B22。

界面测试**刻意不做截图比对**——截图只能证明「看起来对」，证明不了数据对，
而且换台机器、换个缩放率像素就全变了。`tests\test_ui.py` 直接断言控件里的内容
（列表项数、表格行数、缩略图外接框是否含负坐标……）。

打包测试是必须单独做的：PyInstaller 打包后的失败模式跟源码完全不同
（隐藏 import 没收集到、Qt 插件被误排除、单文件解压目录里找不到模块）。
开发时就靠它抓到过一个真 bug——`cli.py` 里写成了 `from .ui import run_ui`，
但 `run_ui` 其实在 `tray.py` 里，源码模式没人跑那条分支，打包后才炸。

写这类端到端测试还有两个坑值得记一下：
- **Win11 记事本默认最大化打开**，而最大化窗口的几何（=整块工作区）在还原引擎里
  是被特殊处理的，测试必须先 `unmaximize()` 再摆位，否则测的不是你要测的流程。
- **PyInstaller 单文件 exe 运行时是两个进程**：父进程是引导进程
  （窗口类 `PyInstallerOnefileHiddenWindow`），子进程才跑 Qt。
  只取 `tasklist` 第一行会拿到引导进程，从而误判「没有窗口」。

## 出问题了怎么看

程序是托盘常驻的，出问题时**看不到任何控制台输出**，所以内置了完整日志。

### 最快的办法：界面上点两个按钮

主界面底部有：

- **「日志…」** —— 直接看到最近的日志（含「刚才那次还原为什么失败」）
- **「导出诊断包…」** —— 把环境信息 + 全部日志打包成一个 zip，方便发给别人看

### 日志在哪

```
%APPDATA%\WindowKeeper\logs\
    windowkeeper.log      ← 人类可读，用记事本打开就行
    windowkeeper.jsonl    ← 机器可读的结构化格式（排查脚本用）
```

同时写两份是有意的：之前只有一份 JSONL，用户打开一看全是花括号，根本读不下去。

### 日志里能看到什么

每次还原，**每个窗口都会记一条**「决定」级别的记录：

```
13:08:54.262  决定  已还原：msedge.exe  [kind=ok  requested=874,155 1132x1121
              actual=874,155 1132x1121  min_track=591x140  score=65
              ambiguous=True  strategy=显示器未变，绝对坐标  cross_monitor=False]
```

| 字段 | 含义 |
|---|---|
| `requested` / `actual` | 期望坐标 vs 实际坐标 —— 一眼看出差在哪 |
| `score` | 匹配分数（≥55 算匹配，≥85 强匹配） |
| `ambiguous` | 是否有同分的孪生候选（需要人工指定） |
| `strategy` | 用了四级几何回退里的哪一级 |
| `cross_monitor` | 是否跨显示器（跨屏会走两步协议） |
| `min_track` | 窗口自身的最小尺寸约束 —— **尺寸差几个像素来自这里，不是 bug** |

有了这几个字段，绝大多数问题不用复现就能定位。举两个真实例子：

- 某窗口尺寸比期望大 2 像素 → 日志显示 `min_track=2562x1601`，
  是窗口自己声明的最小尺寸，**不是程序算错**。
- 报「未找到匹配窗口」→ 日志里有 `score=0` 和 `reasons=['当前没有任何窗口匹配此指纹']`，
  说明那个程序已经退出了。

### 托盘模式崩溃也会留痕

托盘程序没有控制台，异常会静默消失（用户只看到「图标突然没了」）。
程序装了全局异常钩子，未捕获的异常会带完整堆栈写进日志。

### 诊断包里有什么

`诊断报告.txt` + 全部日志与轮转文件。报告含：版本、是否打包运行、Python 版本、
系统版本、**DPI 感知模式**、显示器完整清单（分辨率/缩放/DPI/主屏/工作区）、
预设摘要、日志文件大小。

**隐私说明**：报告里只有窗口标题（本来就是你自己窗口的名字）和显示器参数，
不含账号、文件内容等任何额外信息。

## 已知限制

- **只支持 Windows。** 整个实现建立在 Win32 窗口 API 上。
- **管理员权限的程序管不了。** 一个普通权限的进程无法移动以管理员身份运行的窗口，
  这是 Windows 的 UIPI 机制。要以管理员身份运行本程序才能管那些窗口。
- **全屏独占程序管不了。** 游戏之类的全屏独占窗口不收 `SetWindowPos`。
- **UWP 应用部分受限。** 它们的外层是 `ApplicationFrameWindow`，内层才是实际内容，
  有时候动的是外壳而不是内容。
- **孪生窗口需要人工指定。** 见上面第 3 条。
- **最小化状态下的几何是假的。** 最小化窗口的 `GetWindowRect` 返回 `(-32000,-32000) 160x28`，
  是个哨兵值，程序会特判跳过。
