# 第一部分：模块架构

## 一、分层

```
┌──────────────────────────────────────────────────────────────┐
│  入口层    wk_app.py（打包入口，无参数→托盘 / 带子命令→CLI）      │
│            wk.py（源码入口）  __main__.py（python -m windowkeeper）│
├──────────────────────────────────────────────────────────────┤
│  交互层    cli.py（13 个子命令）  tray.py（托盘+全局热键）        │
│            ui.py（Qt 主界面）      monitor_map.py（显示器缩略图控件）│
├──────────────────────────────────────────────────────────────┤
│  业务层    engine.py（还原引擎，含回读校验）                      │
│            matcher.py（窗口身份识别，四维加权评分）                │
│            store.py（预设存储 + 四级几何回退）                     │
├──────────────────────────────────────────────────────────────┤
│  基础层    win32_api.py（Win32 绑定，唯一直接碰 ctypes 的模块）    │
│            log.py（日志 + 诊断包）                                │
└──────────────────────────────────────────────────────────────┘
```

**关键约定：只有 `win32_api.py` 直接调用 ctypes/Win32。** 其他模块一律走它的封装，
这样 DPI 声明、两步协议、哨兵值处理这些「必须做对的事」只有一处实现，不会漏。

## 三、一次「还原」的完整链路

这是最值得理解的流程，串起了几乎所有模块：

```
用户按热键 / 点菜单 / 点界面按钮
        │
        ├─ tray.HotkeyWatcher.triggered(pid)    ← RegisterHotKey 收到 WM_HOTKEY
        │  （nativeEventFilter 里不直接动窗口，用 QTimer.singleShot(0) 推后）
        ▼
engine.apply_preset(preset, activate, monitors, dry_run)
        │
        ├─ 1. log.decision("开始还原预设", preset=..., windows=..., dry_run=...)
        ├─ 2. store.monitors_changed() 比对保存时的显示器配置
        │      变了 → 记 info，位置改走「相对工作区比例」
        ├─ 3. matcher.enumerate_live_windows()  枚举当前可用窗口
        ├─ 4. matcher.match_preset()  逐个窗口四维加权评分
        │      未匹配 → log.decision("未找到匹配窗口", target=..., score=..., reasons=...)
        ├─ 5. 每个命中的窗口：
        │      ├─ w32.restore_if_minimized() / unmaximize()   ← 失败走 log.swallow()
        │      ├─ store.resolve_geometry()  四级回退算出目标矩形
        │      ├─ w32.get_min_track_size()   查询窗口自身最小尺寸约束
        │      └─ w32.apply_geometry()  ★ 跨屏时内部做两次 SetWindowPos
        ├─ 6. 回读 GetWindowRect 校验 → OutcomeKind(OK/ACCEPTABLE/CONSTRAINED/NOT_FOUND/REFUSED/ERROR)
        ├─ 7. log.decision(f"{status}：{exe}", requested=..., actual=..., score=..., strategy=..., cross_monitor=...)
        └─ 8. log.info("还原「%s」结束：%d/%d 精确，... 耗时 %.0fms")
        ▼
ApplyReport → tray 发气泡通知 / ui 把缩略图换成实际结果
```

**第 7 步那条日志是全项目的排障核心**——它同时记下了期望坐标、实际坐标、匹配分数、
使用的几何策略、是否跨屏、窗口自身的最小约束。用户把日志发回来，就能定位绝大多数问题。

## 四、数据模型

### `WindowRef`（matcher.py）—— 一个窗口的四重几何表示

```python
绝对坐标 (x, y, w, h)                # 最直接，但换显示器就没意义
显示器设备名 + offset_in_work        # \\.\DISPLAY3 + 相对工作区偏移  ← 主力
rel_in_work                          # 相对工作区的比例 (0.0~1.0)     ← 显示器变了用这个
rel_size                             # 相对工作区的尺寸比例
```

### `resolve_geometry()` 四级回退（store.py）—— 显示器配置变了怎么办

| 级别 | 条件 | 策略 |
|---|---|---|
| 1 | 设备名找到且工作区未变 | 用绝对坐标（精确还原） |
| 2 | 设备名找到但工作区变了 | 用相对工作区的偏移与比例换算 |
| 3 | 设备名找不到（屏拔了） | 退到相同序号或主屏，按比例缩放 |
| 4 | 都没有 | 夹回主屏工作区内，保证「至少看得见」 |

**第 4 级是给多屏用户兜底的**——宁可位置不精确，也不能让窗口跑到看不见的地方。

### `ApplyReport`（engine.py）—— 还原结果

```python
total              总窗口数
ok_count           精确还原数
constrained_count  受窗口自身约束（如最小尺寸）而受限
acceptable_count   有偏差但在容忍范围内
failed             list[WindowOutcome]   ← ★ 注意是列表不是计数
touched            实际动过的窗口数
perfect            total > 0 and ok_count == total
```
> 踩过的坑：曾误写成 `report.exact_count` / `report.failed_count`，这两个属性**不存在**，抛
> `AttributeError: 'ApplyReport' object has no attribute 'exact_count'`。正确写法是
> `report.ok_count` / `report.total` / `len(report.failed)`。

### `OutcomeKind`（engine.py）

`OK` / `ACCEPTABLE` / `CONSTRAINED` / `NOT_FOUND` / `REFUSED` / `ERROR`
CLI 把它们映射成前缀 `[OK]` `[WARN]` `[LIMIT]` `[MISS]` `[DENY]` `[FAIL]`。

## 五、存储

- 数据目录：**`%APPDATA%\WindowKeeper\`**（`presets.json` + `logs\`）
- **原子写入**：先写临时文件再 `os.replace()`，避免写一半断电损坏
- `SCHEMA_VERSION = 1`，带版本号便于将来迁移
- 损坏文件容错：JSON 解析失败不会让程序崩，会保留现场并从头开始
- 同名导入自动改名，不覆盖

## 六、日志

- 位置：`%APPDATA%\WindowKeeper\logs\`
- **双格式**：`windowkeeper.log`（人读）+ `windowkeeper.jsonl`（机器读）
  - 人读格式：`HH:MM:SS.mmm  级别  消息  [k=v  k=v]`
  - 级别用中文缩写：DEBUG/INFO/**决定**/警告/错误/致命
- **自定义级别 `DECISION = 25`**：把「引擎的业务决策」和普通 INFO 分开
  （还原时默认想看到「把哪个窗口从哪挪到哪」，但不想淹没在调试信息里）
- `swallow(what, exc, **fields)`：把原来的 `except Exception: pass` 换成它，
  **控制流完全不变（照样继续跑），但痕迹留下了**
- 轮转：1MB × 3 份
- `make_diagnostic_zip()`：导出到桌面的 `WindowKeeper诊断_时间戳.zip`，
  内含环境报告（版本/DPI/显示器/预设摘要）+ 全部日志

# 第二部分：设计约束（★ 重点，全部来自本机实测）

> 以下所有数据都是实测的，不是理论推导。**改代码前必须读这一节。**
> 原始实验代码在 `02_诊断脚本\`，结论的源文件是 `CONCLUSIONS.py`。

环境：Windows / 三显示器 / 混合缩放 [100%, 125%, 150%] / Python 3.13.2

## 结论 1：窗口枚举可行，但有 5 条过滤规则和 1 个哨兵值

实测：`EnumWindows` 枚举到 **424 个**顶层窗口，过滤后只剩 **16 个**真实可用。
过滤统计：不可见 390 / 无标题 15 / 工具窗口 3。

五条规则缺一不可：`IsWindowVisible` / `GetWindowTextLengthW > 0` / 排除 `WS_EX_TOOLWINDOW` /
排除最小化哨兵值 / **排除零尺寸窗口**。

> ★ **最小化窗口的 `GetWindowRect` 返回 `(-32000,-32000) 160x28`。**
> 这是必须硬编码识别的哨兵值，否则会把垃圾坐标存进预设。

> ★ **零尺寸窗口**（可见、非最小化，但 rect 宽或高为 0）也要排除。
> 实测碰到的是 InstallShield 安装程序刚弹出时的 `setup.exe`（类 `InstallShield_Win`，
> `rect=(1280,720,1280,720)`）。这是瞬时状态，存进预设毫无意义，
> 却会破坏「所有窗口都有几何」这条不变量。见 `04_BUG清单.md` 的 B21。

## 结论 2：窗口指纹可辨识，但孪生窗口无法区分

| 程序 | 窗口数 | 现象 |
|---|---|---|
| `explorer.exe` | 4 | 类名全部相同（`CabinetWClass`），只能靠标题区分 |
| `msedge.exe` | 4 | 类名全部相同（`Chrome_WidgetWin_1`），标题含「和另外 N 个页面」会随标签页变化 |
| `video-player.exe` | 3 | **两个 `Chrome_WidgetWin_1` 标题完全相同 → 指纹无法区分** |

> ★ 存在「同进程 + 同类名 + 同标题」的窗口对。必须引入**几何位置近似度**作为最后一级仲裁，
> 并接受「可能匹配到孪生窗口」这一现实，在 UI 上让用户手动修正。

## 结论 3：SetWindowPos 普通权限即可用

实测：记事本 (1747,174) → (1807,234) 返回 True、err=0；684x914 → 564x794 成功；还原后矩形完全一致。
**无需提权**（对本机这些目标而言）。

## ★★ 结论 4：跨屏移动 + 改尺寸必须分两步（本项目最重要的发现）

实测数据（目标：文件资源管理器，三屏缩放 100% / 150% / 125%）：

| 组 | 场景 | 结果 |
|---|---|---|
| 组1 | 同屏原地改尺寸 | 800x600 → 800x600 ✅ 精确 |
| 组2 | 同屏内移动 + 改尺寸 | 800x600 → 800x600 ✅ 精确 |
| 组3 | **跨屏移动 + 改尺寸（一次调用）** | 800x600 → **1200x900** ❌ ×1.5<br>800x600 → **667x500** ❌ ×0.8337 |
| 组4 | **先跨屏移动，再单独改尺寸** | 750x550 → 750x550 ✅ 精确 |

**根因**：在**同一次 `SetWindowPos` 调用**中同时改变窗口所属显示器与尺寸时，
系统按【旧显示器】的 DPI 解释尺寸参数，窗口落到新屏后按【新 DPI】重算，
产生乘性偏差：`新尺寸 = 请求尺寸 × (新屏DPI / 旧屏DPI)`。

**验证**：150% ÷ 100% = 1.5 → 800 × 1.5 = 1200 ✓ 吻合；100% ÷ 120% = 0.8333 → 800 × 0.8333 = 667 ✓ 吻合。

> ★ **对策**：还原跨屏窗口必须调用两次 `SetWindowPos`——第 1 次只设位置，第 2 次只设尺寸。
> 组4 证明两步法可把误差完全消除。**这条已封装在 `win32_api.apply_geometry()` 里，不要绕过它。**
>
> ★ **位置坐标从不受影响**：三组实验中位置永远精确命中，包括负坐标屏 `(-1440,-834)`。
> → 位置可以直接用物理像素存取，无需换算。

## 结论 5：DPI 感知模式不改变上述行为，但 PMV2 仍必须设

实测：unaware / system / pmv2 三种模式下，组3 的缩放倍数**完全一致**。
pmv2 下 `SetProcessDpiAwarenessContext(-4)` 返回 True，`GetProcessDpiAwareness` 从 0 变 2，确实生效。
但跨屏偏差依然存在 → **这个偏差与进程 DPI 感知无关**，是窗口管理器的显示器迁移逻辑本身造成的。

> ★ **但 PMV2 仍然必须设置**，理由不是修这个 bug，而是：
> - UNAWARE 下 `GetMonitorInfo` 返回**虚拟化后的逻辑坐标**：本机实测 150% 屏被报成 **1707x1067** 而不是真实的 **2560x1600**
> - PMV2 下才能拿到真实物理矩形 `(23,-1600)-(2583,0)` 与正确 `dpi=144`
> - 存储预设需要正确的物理尺寸，否则换显示配置后完全错乱

> ⚠️ **易错点**：`PROCESS_DPI_AWARENESS = {0:"UNAWARE", 1:"SYSTEM_AWARE", 2:"PER_MONITOR_AWARE"}`
> 对应的是**老 API** `shcore.GetProcessDpiAwareness()`，**只有三档，没有 V2**。
> V2 是用 `SetProcessDpiAwarenessContext(-4)` 引入的「上下文」概念，设了 V2 老 API 照样只回 `2`。
> 曾经把 `2` 误读成 V2 并据此制造过一次假警报。要确认 V2 请用
> `win32_api.dpi_awareness_context()`（内部走 `GetProcessDpiAwarenessContext`，返回 -4 才是 V2）。

## 结论 6：多显示器原点各不相同且含负坐标

本机实况：

| 序号 | 设备名 | 物理矩形 | 缩放 | 备注 |
|---|---|---|---|---|
| 0 | `\\.\DISPLAY1` | (0,0)-(2560,1440) | 100% | 主屏 |
| 1 | `\\.\DISPLAY3` | (23,-1600)-(2583,0) | 150% | 纵向偏上，x 有 23 偏移 |
| 2 | `\\.\DISPLAY2` | (-1440,-834)-(0,1726) | 125% | 竖屏，**负坐标** |

> ★ 预设**不能只存绝对坐标**，必须同时记录「所属显示器设备名 + 相对该屏工作区的偏移」。
> 还原时先按设备名找屏，找不到再退回「按序号」或「按主屏」，并在 UI 上明确提示「显示器配置已变化」。
> 缩略图控件 `_bounds()` 必须把所有显示器和窗口并成外接框，**不能假设坐标都是正的**。

## 结论 7：哪些窗口管不了

| 类型 | 现象 | 对策 |
|---|---|---|
| `TkTopLevel`（Tkinter） | 完全不响应尺寸参数，调用返回成功但尺寸纹丝不动（三个 DPI 模式都一样），因为 Tk 在 `Configure` 事件里把尺寸改回去了 | 列入「尽力而为」，还原后校验，失败则提示用户 |
| UWP（`ApplicationFrameHost` 托管，如记事本） | 尺寸请求被 UWP 框架拦截 | 已列入 `UNCONTROLLABLE_HINTS` |
| 全屏独占 / 反作弊游戏 | 不在窗口管理器控制下 | 直接跳过 |
| 常驻工具窗口（输入法、Overlay、Progman） | — | 由 `SHELL_CLASSES` / `SHELL_TITLES` 黑名单排除 |

## 七、由此产生的设计约束清单（D1–D7）

| 编号 | 约束 | 实现位置 |
|---|---|---|
| **D1** | 还原协议必须是「两次 `SetWindowPos`」：先位置，后尺寸 | `win32_api.apply_geometry()` |
| **D2** | 程序启动最早期调用 `SetProcessDpiAwarenessContext(-4)`，早于任何窗口/控件创建 | `wk_app.main()` / `cli.main()` 第一行 |
| **D3** | 存储模型用 {显示器设备名, 相对工作区偏移, 物理尺寸} 三元组，而非绝对坐标 | `store.WindowRef` + `resolve_geometry()` |
| **D4** | 匹配算法按 进程名 → 类名 → 标题 → 几何近似度 四级仲裁；接受孪生窗口不可区分，提供 UI 手动指定 | `matcher.score_match()` |
| **D5** | 最小化窗口的 `(-32000,-32000)` 哨兵值必须特判 | `win32_api.is_minimized_geometry()` |
| **D6** | 每次还原后必须回读 `GetWindowRect` 做校验，把「静默失败」变成明确提示 | `engine.apply_preset()` 回读段 |
| **D7** | 无法保证成功的窗口类型（Tk/UWP/全屏）要在 UI 上标注，不承诺 100% 成功 | `engine.UNCONTROLLABLE_HINTS` |

## 八、其他实测得到的工程结论（不在 D1–D7 内，但同样重要）

### 热键：用 `RegisterHotKey`，不要用 `keyboard` 库

`02_诊断脚本\probe_hotkey_impl.py` 做的对照实验，同一台机器、同样注入 `ctrl+alt+1`：

| 方案 | 结果 |
|---|---|
| Win32 `RegisterHotKey` + 消息循环 | ✅ 收到 `WM_HOTKEY`，wParam=40961 |
| `keyboard` 库后台线程监听 | ❌ 回调 **0 次** |

进一步定位（`diag_keyboard_lib.py`）：**普通按键 `a` 能收到，组合键回调 0 次**。
根因：keyboard 库走低级键盘钩子 `WH_KEYBOARD_LL`，需要挂在持续泵消息的线程上，
否则被系统按 `LowLevelHooksTimeout`（默认 300ms）静默摘掉；且它在后台线程里与 Qt 主线程消息循环存在竞争。

**选 `RegisterHotKey` 的三条理由**：① 零第三方依赖 ② `RegisterHotKey(None, id, ...)` 把 WM_HOTKEY 投给调用线程的消息队列，而 `QApplication.exec()` 本来就在泵消息，**不需要任何后台线程** ③ 内核级注册，不受钩子超时限制。

### ★ MSG 结构的 `wParam` 偏移是 16，不是手算的 12

64 位下 MSG 布局：`hWnd(0)/message(8)/wParam(16)/lParam(24)/time(32)/pt(36)`，`sizeof(MSG)=48`。
**因为 WPARAM 是 8 字节，编译器在 4 字节的 `message` 后补了 4 字节对齐。**

第一版手算 `sizeof(HWND)+sizeof(UINT)` = 12，**错了**。症状极具误导性：
**`RegisterHotKey` 成功、错误码 0，但按下去毫无反应。**

诊断手段（`diag_hotkey_owner.py`）：新开进程尝试注册同名热键，返回
**1409 = `ERROR_HOTKEY_ALREADY_REGISTERED`** → 证明托盘进程确实占着热键，问题在消息解析而非注册。

修法：让 ctypes 自己算偏移，不要手算——
```python
msg = ctypes.cast(int(message), ctypes.POINTER(wintypes.MSG)).contents
```
固化在 `tests\test_hotkey.py` 与 `02_诊断脚本\check_msg_layout.py`。

### 打包：`excludes` 管不住 Qt 的 DLL

`excludes` 只作用于 Python 模块；Qt 的 DLL 是 PySide6 的 PyInstaller hook 无差别收集的，**必须手工过滤**。

第一版 45.9MB 里躺着：`opengl32sw.dll` 7.31MB、`Qt6Gui.dll` 4.09、`Qt6Core.dll` 3.53、
`Qt6Quick.dll` 2.97、`Qt6Widgets.dll` 2.80、`python313.dll` 2.37、`Qt6Pdf.dll` 2.35、`Qt6Qml.dll` 2.03、`libcrypto-3.dll` 1.77。

修法：在 `wk.spec` 里 `Analysis` 之后、`PYZ`/`EXE` 之前手工过滤 `a.binaries` / `a.datas`。
实测剔除 **20 个**用不到的 Qt 组件，**45.9MB → 26.2MB**。

> ★ **必须保留**：`Qt6Core` / `Qt6Gui` / `Qt6Widgets` 三个 DLL、平台插件 `qwindows.dll`、
> 样式插件 `qmodernwindowsstyle.dll`、MSVC 运行库。少任何一个 Qt 起不来。

### 打包的两个坑

1. **打包前必须关掉正在运行的 `WindowKeeper.exe`**，否则 exe 被占用，
   `PermissionError [WinError 5]` 出现在构建的**最后一步**，误导性极强。`build.py` 里已自动 `taskkill`。
2. **PyInstaller 单文件 exe 运行时是两个进程**：父进程是引导进程
   （窗口类 `PyInstallerOnefileHiddenWindow`），子进程才跑 Python/Qt。
   只取 `tasklist` 第一行会拿到引导进程，从而误判「主界面没开出来」。
   测试必须收集所有同名 PID 一起枚举窗口。

### `console=False` 的 exe 抓不到管道输出

它会一直阻塞在 Qt 事件循环。要改用 shell 文件重定向
`'"exe" ui > out.txt 2> err.txt'`，靠「窗口是否真的出现」判断成功，而不是靠进程退出码。
