## 一、编码规范

### 命名

| 对象 | 规范 | 示例 |
|---|---|---|
| 模块 | 小写下划线 | `win32_api.py` `monitor_map.py` |
| 类 | 大驼峰 | `PresetStore` `HotkeyWatcher` `MonitorInfo` |
| 函数/变量 | 小写下划线 | `apply_geometry()` `resolve_geometry()` |
| 常量 | 大写下划线 | `MATCH_THRESHOLD` `SHELL_CLASSES` `DECISION` |
| 私有 | 单下划线前缀 | `_configured` `_map_rect()` `_busy` |

**源码命名保持技术栈规范（英文）**；只有面向用户的字符串、界面文字、注释、文档用中文。

### 类型标注

公开函数**必须**标注。项目里已经这么做了，请保持：

```python
def apply_geometry(hwnd: int, x: int, y: int, w: int, h: int,
                   monitors: list[MonitorInfo]) -> tuple[bool, bool]:
def resolve_geometry(self, monitors: list[MonitorInfo]) -> ResolvedGeometry:
```

用 `from __future__ import annotations` 时可以用新语法。数据类用 `@dataclass`：

```python
@dataclass
class MonitorInfo:
    index: int
    name: str
    rect: tuple[int, int, int, int]
    work: tuple[int, int, int, int]
    dpi: int
    primary: bool
```

### 文档字符串

**每个模块头部必须有 docstring，说明「这个模块为什么存在」而不只是「它是什么」。**
本项目所有模块都做到了，请保持。写「为什么」的例子：

```python
"""
统一测试入口 —— 一条命令跑完全部回归套件。

为什么需要这个文件：
    测试原先散在 tests\ 下，各自用 sys.path.insert(0, ".") 找模块，
    只有在「当前目录恰好是 01_WindowKeeper」时才跑得通；换个目录就报
    ModuleNotFoundError: No module named 'windowkeeper'。
"""
```

**关键决策要写「为什么选它而不是另一个」**。例：

```python
# 热键用 RegisterHotKey 而不是 keyboard 库，理由：
#   ① 零第三方依赖 ② 把 WM_HOTKEY 投给调用线程的消息队列，
#   而 QApplication.exec() 本来就在泵消息，不需要后台线程
#   ③ 内核级注册，不受低级钩子 LowLevelHooksTimeout 限制
```

## 二、★ 硬性红线

违反这些会引入已经踩过的坑。**每条都有实测依据。**

### R1 · `enable_per_monitor_v2()` 必须在任何窗口操作之前

```python
def main() -> int:
    w32.enable_per_monitor_v2()      # ← 第一件事
    ...
```
**为什么**：不调用会拿到虚拟化逻辑坐标，150% 屏被报成 1707x1067 而不是 2560x1600。
诊断报告曾因此谎报显示器状态，而那份报告恰恰是用来排障的。

函数是**幂等**的，可以放心重复调用。

### R2 · 不要绕过 `apply_geometry()`

跨屏还原必须**两次** `SetWindowPos`（先位置后尺寸），这条已封装在里面。
**为什么**：同一次调用同时改显示器归属和尺寸，系统按旧屏 DPI 解释尺寸，偏差 = 新DPI/旧DPI
（实测 800x600 → 1200x900，正好 ×1.5）。

### R3 · 只有 `win32_api.py` 可以直接调用 ctypes

其他模块一律走它的封装。
**为什么**：DPI 声明、两步协议、哨兵值特判这些「必须做对的事」只有一处实现，不会漏。

### R4 · 热键用 `RegisterHotKey`，不要换回 `keyboard` 库

**为什么**：实测本机 keyboard 库「普通按键 `a` 能收到、组合键回调 0 次」。

### R5 · `nativeEventFilter` 里不要直接动窗口

```python
# 对：推到下一轮事件循环
QTimer.singleShot(0, lambda: self.triggered.emit(pid))
```
**为什么**：在事件过滤器里做耗时操作会卡住消息循环。

### R6 · 不要为了让测试通过而删断言

`tests\` 里的断言大多固化的是真踩过的坑。**宁可标记 skip 并写明原因，也不要删。**
例：`test_hotkey.py` 里同时断言「`wParam` 偏移是 16」和「手算得的 12 是错的」。

### R7 · 日志系统自身不能成为崩溃源

- 每个 handler 创建都包在 try/except 里
- `setup()` 幂等（`_configured = bool(logger.handlers)`）
- `swallow()` **保持控制流完全不变**，只留痕迹

### R8 · 界面测试断言内容，不要截图比对

**为什么**：截图只能证明「看起来对」，证明不了「数据对不对」；换台机器换缩放率像素就全变。

## 三、改代码的流程

### 1. 改动前

- **确认项目不是 git 仓库** → 重要改动前先做增量备份
  （完整备份是 `_backup_20261014\`，用 `robocopy <项目> <备份>/E`）
- 想清楚属于哪一层：改 Win32 行为 → `win32_api.py`；改匹配 → `matcher.py`；改几何回退 → `store.py`

### 2. 改动中

- **一次只改一件事**，方便定位问题
- 遇到 `except Exception: pass` → 换成 `log.swallow("正在做什么", exc, **上下文)`
- 新的静默失败点必须有日志，否则将来无从排查

### 3. 改动后（检查清单）

```powershell
# 必须：全量回归
python 01_WindowKeeper\run_tests.py

# 改了界面 → 真看一眼
python 01_WindowKeeper\wk.py ui

# 改了引擎/匹配 → 预演（不动窗口）
python 01_WindowKeeper\wk.py list
python 01_WindowKeeper\wk.py apply <预设名> -n

# 改了打包配置 → 重新打包 + 打包验收
python 01_WindowKeeper\build.py
python 01_WindowKeeper\run_tests.py --all
```

- 在 [05_更新日志.md](05_更新日志.md) 追加一条
- 有新踩的坑 → 写进 [04_BUG清单.md](04_BUG清单.md)（含**原始报错文本**，方便将来 grep）

## 四、加新功能时

### 加一个 CLI 子命令

1. `cli.py` 的 `build_parser()` 里加子命令，绑定 `cmd_xxx`
2. 在 `wk_app.py` 的 `cli_words` 白名单里**加上这个词**
   （⚠️ 忘了加的话，打包后的 exe 会把子命令当成「无参数」而启动托盘）
3. 成功时 `log.get("cli").info("命令结束", command=..., exit_code=code)`
4. 结果用 `_say()` 输出，状态前缀用 `_MARK` 里现有的 `[OK]/[WARN]/[LIMIT]/[MISS]/[DENY]/[FAIL]`

### 加一个预设字段

1. `store.py` 的 `Preset` dataclass 加字段**并给默认值**（保证旧预设能反序列化）
2. **`SCHEMA_VERSION` 加 1**，并在加载逻辑里写迁移
3. 更新导入/导出的序列化
4. `tests/test_engine.py` 存储往返组加断言

### 加一个测试套件

1. 在 `tests\` 建 `test_xxx.py`，顶部**必须**用
   `sys.path.insert(0, str(Path(__file__).resolve().parent.parent))`（**不要用 `"."`**）
2. 输出末尾必须有 `通过 N / 共 M` 格式的汇总行（`run_tests.py` 靠它判定）
3. 输出前 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`
4. 在 `run_tests.py` 的 `SUITES` 列表里注册，选对 `group`（fast / slow / pack）

## 六、关于「不要过度重构」

项目当前 9 个模块职责清晰、无重复代码、无循环依赖。**没有重构的必要。**

曾被考虑但**明确不做**的：

| 想法 | 为什么不做 |
|---|---|
| 拆 `ui.py`（41KB） | 拆分收益不大，且会打散界面状态管理的连贯性 |
| 引入插件架构 | 收益为零，风险不小 |
| 换掉 ctypes 用现成库 | `win32_api.py` 已封装良好，换库要重验所有实测结论 |
| 加类型检查器/格式化器 | 当前代码风格一致；引入工具会带来配置负担 |

**判断标准**：重构是否解决了某个**实际遇到的问题**？如果只是「看起来更整洁」，不做。
